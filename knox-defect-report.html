01Summary

The defects cluster into one pattern. Knox stores what an agent tells it to store, keyed by strings the agent chooses. Nothing validates that those strings describe the same file or the same project twice in a row, and nothing checks whether a read ever returned anything. The critical four are all instances of that single weakness.

The failure mode

A guardrail call that should return three architectural constraints returns zero rows, formatted correctly, with "pass": true. The agent proceeds. No log records the empty result, no counter moves, and the desktop UI shows a healthy database. This is why the defects below matter more than their count suggests.

Verification method

Every snippet on this page was read out of the repository at build time, so the line numbers are the real ones. Two behaviours (D-01, D-02, D-03) were reproduced by porting the functions line for line into Python and running them against the project's own schema and SQL - see section 07. The crate was not compiled: no Rust toolchain was available, so no claim here rests on running Knox itself.

02Critical

These four produce wrong answers that look right. Each one alone is enough to make the graph untrustworthy for file-scoped questions.

D-01 Critical src/ingest/summary.rs:230

Path normaliser hard-codes the name of this project

Every file-scoped write and read passes through normalize_file_path. Line 231 scans the path segments for a directory literally called knox and, if it finds one, throws away everything before it. That makes the author's own repository work and corrupts everyone else's.

rust src/ingest/summary.rs:230–235
230    // If 'knox' appears as a folder component, take relative path after it
231    if let Some(pos) = segments.iter().position(|s| s.eq_ignore_ascii_case("knox")) {
232        if pos + 1 < segments.len() {
233            return segments[pos + 1..].join("/");
234        }
235    }
Effect

A project at /home/diva/knox/app/src/main.rs is stored as app/src/main.rs. A project at /home/diva/projects/payments-api/knox/src/lib.rs is stored as src/lib.rs - and now collides with every other src/lib.rs in the database.

Fix

Delete the block. Path identity belongs in a typed constructor that resolves against a known project root, not in a string cleaner that guesses at one.

D-02 Critical src/ingest/summary.rs:218

Absolute POSIX paths can never match relative queries

The same function strips a Windows drive letter but nothing else. On macOS and Linux there is no colon, so the leading slash is dropped and the entire directory chain is kept: an absolute path becomes home/diva/projects/api/src/lib.rs while a relative query becomes src/lib.rs.

223    };
224
225    let segments: Vec<&str> = without_drive

227        .filter(|s| !s.is_empty() && *s != ".")

The two never match. Replayed against the real action_files lookup, a file recorded by absolute path returns zero rows to a relative-path query - so knox_check_guardrails reports pass: true with no constraints on a file that has them. The safety check fails open.

D-05 High src/mcp/handlers/record_action.rs:103

Session reuse ignores the project when the caller omits it

Auto-session resolution scans the twenty most recent sessions and reuses the first open one belonging to the same actor. The project is compared only when the caller supplied one; when project is None - which the schema permits - any open session for that actor is adopted.

Relation types carry direction - depends_on, implements, reverts. The recursive CTE that loads a subgraph matches them in both directions, so the component it returns cannot distinguish what an action points at from what points at it.

D-14 Medium src/commands/hook.rs:9

The installed hook can block every commit

The generated script runs knox scan --project . with no PATH fallback and no failure guard. If knox is not on the PATH of the process running git - an IDE, a GUI client - the hook exits non-zero.

rust src/commands/hook.rs:9–12

Effect

Fix

Resolve the binary by absolute path at install time and end the script with a success exit.

D-15 Medium src/storage/db.rs:40

Four processes write to one SQLite file with no retry

The connection sets WAL, foreign keys and synchronous=NORMAL, and nothing else. No explicit busy timeout, no retry, no checkpoint policy.

rust src/storage/db.rs:40–43
40        let conn = Connection::open(path)?;
41        let _: String = conn.query_row("PRAGMA journal_mode = WAL", [], |r| r.get(0))?;
42        conn.pragma_update(None, "foreign_keys", "ON")?;

Effect

The desktop app, one server per agent, the CLI and the hook all write here. WAL allows one writer; rusqlite's five-second default means a blocked write stalls a tool call and can still fail with SQLITE_BUSY, which surfaces to the agent as a generic internal error.

Fix

Set the timeout deliberately, retry with jitter, map busy to a retryable error with a hint.

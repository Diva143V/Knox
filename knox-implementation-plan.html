Remediation plan · storage, models, graph usage Four places where the app knows something the user cannot see Every shortcoming in this plan is the same shape: the mechanism is correct and the user is not told. A mode switch that silently changes which database you are in, a model layer with no panel, a graph counter that measures the wrong table. Ten days, four phases. That is four days of Phase 2, and it is the phase that unlocks the most capability for the least new code. 02 The decision: one database, always Global mode becomes the only mode. The toggle is removed from the UI, and every project shares one file — isolation comes from the project_id column and remote-based identity, not from separate databases. Why Detail Isolation already exists without it Every action carries project_id; every read filters by it; clones and worktrees resolve to one project by git remote. Separate files were never the isolation mechanism Two modes created the worst failure in this plan A user can be looking at one database while their agent writes to another, with nothing on screen saying so The MCP server resolves from its own cwd In project-local mode, an agent launched outside the repo writes to a different file than the app shows — and there is no way to notice A global file is what the product is for Memory that survives a repo move, a clone, or a second machine checkout is the point of an external memory layer Cost of removal is small and known 8 files reference global_mode; two of them are UI surfaces The risk removal creates, and the only way to take it safely Anyone already running project-local has data in /.knox/knox.db. Remove the mode without a consolidation path and their memory becomes invisible — the exact data-trust failure Phase 1 was written to fix. So the toggle comes out in the same release that adds detection and import of existing project-local databases. Not before. 03 Objective, and what fixed looks like Not “add features”. Make the four existing subsystems legible to a user who never opens a terminal. Objective Done when Storage mode is never a silent switch Changing mode names both databases and their row counts before it happens, and offers to move the data Models are configurable without a shell A user enables a local model, tests it, and asks a question — three clicks, no env vars Graph usage is visible The panel shows edges and relations separately, and explains a zero Storage maintenance does what the button says Vacuum returns the WAL to near zero and the number stops looking alarming 04 The shortcomings, decomposed ID Shortcoming Evidence Cost to user Class S1 Mode switch changes the database with no warning and no migration StorageTab.tsx writes global_mode;
